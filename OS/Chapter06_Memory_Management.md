## 6.1 Memory Hierarchy: The Foundation

### The Path of Elegance

```
Registers (1 cycle, 1 KB)
    ↓

    ↓
```

## 6.2 Address Binding: The Translation Problem

### Three Binding Times

1. **Compile Time:** Absolute addresses in binary
   - **Problem:** Cannot move program in memory
   - **Use:** Embedded systems with fixed memory layout

2. **Load Time:** Relocatable addresses, resolved at load
   - **Problem:** Cannot move once loaded
   - **Use:** Old OS (MS-DOS)

3. **Execution Time:** Dynamic address translation
   - **Solution:** Modern OS with **virtual memory**
   - **Mechanism:** Hardware MMU (Memory Management Unit)

**The 2026 Trap:**

**Question:** "Which binding allows process relocation during execution?"

**Answer:** **Execution-time binding** only.

## 6.3 Logical vs Physical Address

### The Dichotomy

| **Address Type** | **Where** | **Generated By** | **Visible To** |
|------------------|-----------|------------------|----------------|
| **Logical (Virtual)** | Program | CPU (instructions) | Process |
| **Physical** | RAM | MMU (translation) | Hardware |

**The Mapping:**

$$\text{Logical Address} \xrightarrow{\text{MMU}} \text{Physical Address}$$

**Example:**
- Process references address `0x1000` (logical)
- MMU translates to `0x5000` (physical)

**The Golden Pivot:** Logical address space is **process-specific**, physical is **system-wide**.

## 6.4 Contiguous Memory Allocation

### Fixed Partitioning

**Mechanism:** Divide memory into fixed-size partitions.

**Problems:**
1. **Internal Fragmentation:** Partition size > process size → wasted space inside partition
2. **Limit on degree of multiprogramming:** Number of partitions = max processes

**Example:**
- Partition size: 100 KB
- Process needs: 80 KB
- Wasted: 20 KB (internal fragmentation)

### Variable Partitioning

**Mechanism:** Allocate exactly the size needed.

**Allocation Strategies:**

#### 1. First Fit
**Rule:** Allocate first hole large enough.

**Pros:** Fast (no exhaustive search)
**Cons:** Creates small holes at beginning

#### 2. Best Fit
**Rule:** Allocate smallest hole large enough.

**Pros:** Minimizes wasted space per allocation
**Cons:** Slow (must search entire list), creates tiny unusable holes

#### 3. Worst Fit
**Rule:** Allocate largest hole.

**Pros:** Leftover hole is larger (more usable)
**Cons:** Slow, eliminates large holes (bad for large processes)

### External Fragmentation

**Problem:** Total free space sufficient, but **not contiguous**.

**Example:**
- Free: [20 KB] [30 KB] [25 KB]
- Total free: 75 KB
- Process needs: 50 KB
- **Cannot allocate** (no single 50 KB hole)

**Solution: Compaction**

**Mechanism:** Move processes to create one large contiguous hole.

**Cost:** $O(n)$ copying, **high overhead**.

**The 2026 Adversarial Vault:**

**Trap:** "Best Fit minimizes external fragmentation."
- **FALSE.** Best Fit creates **more** small unusable holes.
- **First Fit** typically performs better in practice.

## 6.5 Fragmentation: The Two Evils

### Internal Fragmentation

**Definition:** Wasted space **inside** allocated region.

**Causes:**
- Fixed-size allocation (partition larger than needed)
- Alignment requirements (allocate in 4 KB pages, process needs 3.5 KB)

**Formula:**
$$\text{Internal Frag} = \text{Allocated Size} - \text{Actual Size}$$

### External Fragmentation

**Definition:** Wasted space **between** allocated regions (total free sufficient but not contiguous).

**Formula:**
$$\text{External Frag} = \text{Total Free} - \text{Largest Free Block}$$

**The Mental Machinery:**
- **Internal:** Like empty seats in a reserved theater row
- **External:** Like scattered empty seats across the theater

## 6.6 Paging: The Fragmentation Solution

### The Atomic Truth
**Paging = Divide memory into fixed-size blocks**

### The Mechanism

**Physical Memory:** Divided into **frames** (fixed size, e.g., 4 KB)
**Logical Memory:** Divided into **pages** (same size as frames)

**Page Size = Frame Size** (typically 4 KB, 2 MB, 1 GB)

**Mapping:** Page → Frame via **Page Table**

### Address Translation

**Logical Address:**
```
| Page Number (p) | Offset (d) |
```

**Formula:**
$$\text{Logical Address} = p \times \text{Page Size} + d$$

**Translation:**
1. Extract page number $p$ and offset $d$
2. Look up Page Table: $\text{Frame Number } f = \text{PageTable}[p]$
3. Compute Physical Address: $\text{Physical} = f \times \text{Page Size} + d$

### Example

**Page Size = 1 KB = 1024 bytes**

**Logical Address = 2500**

**Step 1:** Convert to binary or divide:
$$p = \lfloor 2500 / 1024 \rfloor = 2$$
$$d = 2500 \mod 1024 = 452$$

**Step 2:** Page Table lookup:
$$\text{PageTable}[2] = 7$$ (frame number)

**Step 3:** Physical Address:
$$\text{Physical} = 7 \times 1024 + 452 = 7168 + 452 = 7620$$

### Page Table Structure

```c
struct PageTableEntry {
    unsigned int frame_number : 20;  // Frame location
    unsigned int valid : 1;          // Page in memory?
    unsigned int protection : 3;     // R/W/X bits
    unsigned int reference : 1;      // Recently accessed?
    unsigned int modified : 1;       // Dirty bit (written to?)
    unsigned int caching : 1;        // Cache policy
};
```

### Advantages of Paging

1. **No external fragmentation** (all frames are same size)
2. **Easy allocation** (any free frame works)
3. **Supports virtual memory** (pages can be on disk)

### Disadvantages

1. **Internal fragmentation** (last page might be partially filled)
   - Average waste: 0.5 × Page Size
   - For 4 KB pages: Average 2 KB waste per process

2. **Page Table overhead** (one entry per page)
   - For 32-bit address space with 4 KB pages: $2^{20}$ entries = 4 MB per process

3. **Translation overhead** (one extra memory access for page table)

### The 2026 Adversarial Vault

**Trap 1:** "Paging eliminates all fragmentation."
- **FALSE.** Eliminates **external**, but **internal** remains (last page).

**Trap 2:** "Larger page size reduces internal fragmentation."
- **FALSE.** Larger pages → **more** internal fragmentation (average = 0.5 × page size).

**Trap 3:** "Offset bits determine page size."
- **TRUE.** If offset = 12 bits, page size = $2^{12}$ = 4 KB.

**NAT Precision Lock:**

**Question:** "32-bit address space, 4 KB pages. How many page table entries?"

**Solution:**
- Page bits: $32 - 12 = 20$ bits
- Entries: $2^{20} = 1,048,576$

**Answer: 1048576**

## 6.7 Translation Lookaside Buffer (TLB)

### The Atomic Truth
**TLB = Cache for Page Table Entries**

### The Problem

Without TLB:
```
Memory Access:
1. Access Page Table (1 memory access)
2. Access Data (1 memory access)
Total: 2 memory accesses
```

**Effective Access Time (EAT) without TLB:**
$$\text{EAT} = 2 \times T_{\text{mem}}$$

### The Solution

**TLB:** Small, fast cache storing recent page table entries.

**Size:** 64-1024 entries (vs millions in page table)

**Access Time:** 1-2 cycles (vs 100 cycles for RAM)

### TLB Hit/Miss

**TLB Hit:** Entry found in TLB → 1 memory access (data only)
**TLB Miss:** Entry not in TLB → 2 memory accesses (page table + data)

### Effective Access Time with TLB

$$\text{EAT} = \alpha \times (T_{\text{TLB}} + T_{\text{mem}}) + (1-\alpha) \times (T_{\text{TLB}} + T_{\text{mem}} + T_{\text{mem}})$$

where $\alpha$ = TLB hit ratio.

**Simplified (assuming $T_{\text{TLB}} \approx 0$):**
$$\text{EAT} = \alpha \times T_{\text{mem}} + (1-\alpha) \times 2T_{\text{mem}}$$
$$\text{EAT} = (2 - \alpha) \times T_{\text{mem}}$$

### Example

**Given:**
- TLB hit ratio: 80%
- Memory access time: 100 ns
- TLB access time: 0 ns (negligible)

**Solution:**
$$\text{EAT} = 0.8 \times 100 + 0.2 \times 200 = 80 + 40 = 120 \text{ ns}$$

**Speedup vs no TLB:**
$$\text{Speedup} = \frac{200}{120} = 1.67\times$$

### The 2026 Adversarial Vault

**Trap:** "TLB miss causes page fault."
- **FALSE.** TLB miss → access page table in memory. **Page fault** occurs when page not in memory (on disk).

**Trap:** "Higher TLB hit ratio → higher EAT."
- **FALSE.** Higher hit ratio → **lower** EAT (faster access).

## 6.8 Multi-Level Paging

### The Problem

**32-bit address space, 4 KB pages:**
- Page table size: $2^{20}$ entries × 4 bytes = 4 MB per process
- For 100 processes: 400 MB just for page tables!

### The Solution: Two-Level Page Table

```
Logical Address: | P1 | P2 | Offset |
```

**Level 1:** Page Directory (points to page tables)
**Level 2:** Page Tables (points to frames)

### Address Translation

1. Extract $P_1$ (outer page table index)
2. Extract $P_2$ (inner page table index)
3. Extract Offset

**Steps:**
1. Access Page Directory at $P_1$ → get Page Table address
2. Access Page Table at $P_2$ → get Frame Number
3. Compute Physical Address: Frame × Page Size + Offset

### Example: Two-Level Paging

**32-bit address, 4 KB pages**

**Bit allocation:**
- Offset: 12 bits (for 4 KB page)
- Remaining: 20 bits (split into two 10-bit page numbers)
- $P_1$: 10 bits (1024 entries in directory)
- $P_2$: 10 bits (1024 entries per page table)

**Advantage:** Page tables created **on-demand** (sparse address spaces don't waste memory).

**Example:**
- Process uses only first 8 MB of address space
- Without multi-level: 4 MB page table (full)
- With multi-level: 1 page directory (4 KB) + 2 page tables (8 KB) = 12 KB

**Savings:** $4 \text{ MB} - 12 \text{ KB} \approx 4 \text{ MB}$

### Three-Level and Beyond

**64-bit address space** requires multiple levels (e.g., x86-64 uses 4 levels).

**Tradeoff:** More levels → less memory overhead but **more access time** (one memory access per level).

## 6.9 Segmentation

### The Atomic Truth
**Segmentation = Logical division matching program structure**

### The Mechanism

**Segments:**
- Code segment
- Data segment
- Stack segment
- Heap segment

Each segment has:
- **Base:** Starting physical address
- **Limit:** Size of segment

### Segment Table

```
| Segment Number | Base Address | Limit |
|----------------|--------------|-------|
| 0 (Code)       | 0x10000      | 5000  |
| 1 (Data)       | 0x20000      | 3000  |
| 2 (Stack)      | 0x30000      | 2000  |
```

### Address Translation

**Logical Address:**
```
| Segment Number (s) | Offset (d) |
```

**Translation:**
1. Check: $d < \text{Limit}[s]$ (bounds checking)
2. If valid: $\text{Physical} = \text{Base}[s] + d$
3. If invalid: **Segmentation Fault** (famous error!)

### Example

**Logical Address:** Segment 1, Offset 500

**Segment Table:**
- Segment 1: Base = 0x20000, Limit = 3000

**Check:** $500 < 3000$ ✓

**Physical:** $0x20000 + 500 = 0x20500$

### Advantages

1. **Logical structure:** Matches program organization
2. **Protection:** Different permissions per segment (code = read-only, data = read-write)
3. **Sharing:** Multiple processes can share code segment

### Disadvantages

1. **External fragmentation:** Segments have variable size
2. **Complexity:** Harder to implement than paging

---

## 6.10 Segmented Paging

### The Best of Both Worlds

**Combine segmentation and paging:**
- Logical view: Segments
- Physical allocation: Pages

**Mechanism:**
1. Logical address → Segment Number + Offset
2. Segment Table entry → Base of Page Table for that segment
3. Offset → Page Number + Page Offset
4. Page Table → Frame Number
5. Physical Address = Frame × Page Size + Page Offset

**Advantages:**
- Logical structure of segmentation
- No external fragmentation (paged allocation)

**Example:** Intel x86 architecture (historical).

## 6.11 Mental Machinery for Permanent Recall

### The Bizarre Mnemonic: "The Library Analogy"

Imagine a **library** (physical memory):

- **Frames:** Shelves (fixed size, numbered)
- **Pages:** Books (fit exactly on shelves)
- **Page Table:** Library catalog (book → shelf mapping)
- **TLB:** Librarian's memory (recent lookups cached)
- **Segments:** Sections (fiction, non-fiction, reference)
- **Internal Fragmentation:** Half-empty shelf (book doesn't fill it)
- **External Fragmentation:** Empty spaces scattered (can't fit large book set)
- **Paging:** Move books individually (any book, any shelf)
- **Segmentation:** Move entire sections (fiction together)

**The Mental Slider:**
- Left (Contiguous): All books in order (fast, but rigid)
- Right (Paged): Books scattered (flexible, but need catalog)

## 6.12 Practice Problems

### MCQ 1: Address Translation

**Q:** 16-bit address space, 1 KB pages. How many bits for page number?

(A) 4  
(B) 6  
(C) 10  
(D) 16  

**Solution:**

Page size = 1 KB = $2^{10}$ bytes → Offset = 10 bits

Page bits = $16 - 10 = 6$ bits

**Answer: (B)**

---

### MCQ 2: TLB

**Q:** TLB hit ratio = 90%, memory access = 100 ns, TLB access = 0 ns. EAT = ?

(A) 100 ns  
(B) 110 ns  
(C) 120 ns  
(D) 190 ns  

**Solution:**

$$\text{EAT} = 0.9 \times 100 + 0.1 \times 200 = 90 + 20 = 110 \text{ ns}$$

**Answer: (B)**

---

### MCQ 3: Internal Fragmentation

**Q:** Page size = 4 KB. Process needs 72 KB + 100 bytes. Internal fragmentation = ?

(A) 0 KB  
(B) 1.9 KB  
(C) 3.9 KB  
(D) 4 KB  

**Solution:**

Total needed: $72 \times 1024 + 100 = 73,828$ bytes

Pages needed: $\lceil 73828 / 4096 \rceil = 19$ pages

Allocated: $19 \times 4096 = 77,824$ bytes

Internal frag: $77,824 - 73,828 = 3,996$ bytes $\approx 3.9$ KB

**Answer: (C)**

---

### MCQ 4: Page Table Size

**Q:** 32-bit address space, 8 KB pages, 4-byte page table entry. Page table size = ?

(A) 2 MB  
(B) 4 MB  
(C) 8 MB  
(D) 16 MB  

**Solution:**

Offset bits: $\log_2(8192) = 13$ bits

Page bits: $32 - 13 = 19$ bits

Entries: $2^{19} = 524,288$

Size: $524,288 \times 4 = 2,097,152$ bytes = 2 MB

**Answer: (A)**

### NAT 1: Logical to Physical

**Q:** Page size = 2 KB. Logical address = 5000. Page table: [0→3, 1→7, 2→5]. Physical address = ?

**Solution:**

$$p = \lfloor 5000 / 2048 \rfloor = 2$$
$$d = 5000 \mod 2048 = 904$$

Frame = PageTable[2] = 5

$$\text{Physical} = 5 \times 2048 + 904 = 10,240 + 904 = 11,144$$

**Answer: 11144**

Offset: $\log_2(16384) = 14$ bits

Page bits: $40 - 14 = 26$ bits

Entries: $2^{26} = 67,108,864$

**Answer: 67108864**
